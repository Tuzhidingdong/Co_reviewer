---
description: Run the Co_Reviewer multi-document peer-review revision workflow
---

1. Run `python scripts/co_reviewer_cli.py audit --rev Reply.docx --man Manuscript.docx --si SI.docx --out workspace_digest.md --json-out workspace_inventory.json --audit-md-out review_audit_report.md --audit-out review_audit_report.json --decision-queue-out review_decision_queue.json --cache-dir .co-reviewer-cache` with whichever files are available; omit missing inputs. This parses each source once per SHA-256 and reuses the inventory cache on later runs.
2. Read the compact digest and deterministic audit. Generate or filter the bounded decision queue for one Word comment ID at a time with `--comment-ids <id>`. Native Word selection text is recovered from the matching comment-range markers; the containing paragraph is separate. Exact unique cross-document matches are confirmed; ambiguous/no matches are unresolved; token-overlap matches remain candidates only.
3. For one selected comment at a time, propose a structured semantic decision conforming to schemas/review-decision.schema.json: disposition (schema values: `manuscript`, `si`, `reply_only`, `manuscript_and_si`, `no_change`, `clarification_needed`), evidence-based rationale, exact proposed targets (document, Word part, paragraph index, action and source excerpt), response outline, supporting evidence, missing evidence/questions and confidence. Keep `requires_user_approval=true`; candidates are not confirmed targets. Show the proposal to the user and build the revision plan only after the user accepts the disposition and target scope.
4. Build a revision plan using schemas/revision-plan.schema.json. Give each concern a stable ID and link it to every affected document target.
5. Before approval, read the complete sentence containing each edit plus adjacent context. Check tense against the surrounding scientific narrative (completed methods/observations usually past; established facts and figure/table content often present), subject–verb agreement, articles, number, parallelism and transitions. Do not mechanically change tense. Show the user the original full sentence, proposed full sentence, exact replacement span and any unresolved language/evidence question.
6. Represent intended subscripts/superscripts with supported Unicode script characters in the plan (for example `SO₄²⁻`), not caret notation or HTML. The revision engine converts supported characters to native Word `w:vertAlign` runs. Inspect the final DOCX formatting; unsupported script characters must be flagged instead of silently left as baseline text.
7. Present the original reviewer comment, proposed response, evidence basis, exact Manuscript/SI edits and unresolved questions. Obtain the user's approval for the selected items; do not apply planned or unapproved items.
8. After explicit approval, run `approve-plan --plan edits_plan.json --ids ...`. This seals the exact reviewer comment, proposed response and target list with a SHA-256 fingerprint. It is an integrity check, not an identity signature; invoke it only after explicit user approval. If any of those fields later change, validation must fail until the revised item is presented and explicitly re-approved.
9. Run validate-plan, then apply. The CLI applies only items marked approved and automatically persists successfully applied items as applied in the plan. Do not manually mark them applied.
10. Run verify --plan ... --apply-report ... to check the exact native Word deletion/insertion revision IDs and text, plus the whole-document audit for untracked text changes. A Marked DOCX must not contain direct text edits outside planned `w:ins`/`w:del` revisions. Use status --plan ... to summarize all planned, approved, applied, verified and blocked items.
11. Re-inspect affected outputs and check tense/grammar in complete sentences, native subscript/superscript formatting, scientific meaning and cross-document consistency (Manuscript/SI values, units, sample names, figure/table numbering and every response claim). Use the numbering audit as a diagnostic report only; it does not renumber. Mechanical verification alone is not semantic verification.
12. Mark only fully checked items as verified. Generate the Response Letter in Markdown with render-response --plan ... or in Word with render-response-docx --plan ... --out Response_to_Reviewers.docx. The renderer must retain draft labels for items not marked verified and must never invent missing replies.
13. Support incremental follow-up: process only newly approved items, reuse inventories when inputs are unchanged, and use the previous revised DOCX as input for later edits to that same document. Reuse the same apply-report path; the CLI appends each iteration so the full revision history remains verifiable. Re-inspect affected files when paragraph structure changes.
14. Return revised files, Response Letter, verification report, task-state summary and unresolved issues. Never claim an edit is complete without checking the output file.


Decision queue rule: use only the affected comment's excerpts from `review_decision_queue.json` for semantic reasoning. Do not reread all three DOCX files when the cache hashes are unchanged. If the queue lacks enough evidence, retrieve only the specific neighboring paragraph/table/figure context that is missing. Decisions remain pending until the user approves the revision plan.
