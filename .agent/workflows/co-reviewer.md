description: Run the Co_Reviewer multi-document peer-review revision workflow
---

1. Identify the active revision round and available Reply/Reviewers, Manuscript and SI DOCX files. Preserve all inputs.
2. Run one `python scripts/co_reviewer_cli.py audit ...` pass for all available files. Reuse the SHA-256/parser-version cache; reparse only a source whose hash changed. Do not reread entire DOCX files when the cached inventory is valid. The round starter also writes zero-model-call historical revision baselines for every copied DOCX.
3. Read the compact digest, deterministic audit and bounded decision queue. By default include all reviewer comments. Use `--comment-ids` only when the user explicitly narrows the requested scope.
4. Complete the whole requested review round in one invocation. Split compound comments into atomic tasks; merge overlapping tasks while retaining every source comment ID. Do not ask the user to submit one comment at a time.
5. Analyse the workspace-level figure/table audit independently of comment anchors. Distinguish true workspace-unresolved references, cross-document matches, subpanel/range references, same-document label collisions, repeated identical captions and cross-document caption reproductions. Caption-text equality does not prove visual-object identity. Never auto-renumber.
6. Map exact candidate targets, then run `targeted-revision-gate` against the matching Manuscript/SI `revision-baseline` before expensive manuscript discovery or any write. If history overlaps, expose exact `structure_id` values and obtain the author's explicit Accept/Reject policy. Use `resolve-historical-revisions` only for supported native text wrappers, paired moves and valid property snapshots; it must write a new DOCX. Comment anchors, table-topology, numbering and unsupported structures remain blocked. After resolving any source, start a fresh round and regenerate all inventories, hashes and approvals.
7. For each task, record its intent, type, affected documents, Word part and paragraph locations, evidence excerpts, match status (confirmed, candidate, ambiguous, unresolved), proposed action, confidence and missing evidence. Candidate evidence must never be promoted to a confirmed target.
8. Build a dependency graph for cross-document tasks. Record prerequisites, reject dependency cycles and assign an execution sequence consistent with the graph. Finish all supported analysis even when individual tasks require clarification.
9. Generate revision_decision_plan.md and revision_decision_plan.json using schemas/revision-decision-plan.schema.json. Include all comments in scope, stable task IDs, source comment IDs, evidence IDs, exact coordinates, target/evidence links, dependencies, readiness, unresolved questions and confidence. All tasks must remain status=pending and requires_user_approval=true.
10. Validate the plan against the current audit and inventory:

       python scripts/validate_decision_plan.py --plan revision_decision_plan.json --audit review_audit_report.json --inventory workspace_inventory.json

   Fix failures. The validator checks structure and evidence provenance, not scientific correctness.
11. Build one consolidated Plan and atomic instruction Coverage. The agent reviews exact target matches, full sentence context, scientific notation and cross-document dependencies. A decision plan is an audit record, not a routine request for the author to reapprove their own instructions.
12. Run no-write preflight. For explicit, conflict-free author instructions, create a hash-bound `instruction_based_authorization` from the preflighted Plan, Coverage and complete scope assessment, then execute without another routine author approval. If an operation needs scientific invention, contains unresolved conflict, lacks a reliable target/evidence link, expands scope or is marked `author_approval`, pause only that work and ask one focused question.
13. The `instruction_based_authorization` is a machine record, never an author signature. It must bind the original instruction SHA-256, exact Plan/Coverage file and manifest hashes, all input DOCX hashes, each target scope, and an assessment with no unresolved conflicts, uncovered requirements or out-of-scope targets. Any source/Plan/Coverage change invalidates it.
14. Apply only through official CLI Apply after current Preflight and authorization validation. Inputs remain immutable and every Marked textual change uses native Word Track Changes. Unsupported targets fail closed. For genuinely author-adjudicated tasks, retain the distinct `author_approval` path.
15. Run independent Verify; it must reread source and actual outputs and independently check Track Changes, untracked-text integrity and character-level formatting. Agent-performed semantic/cross-document review may confirm verified tasks; do not claim human review unless the author performed it. Render response drafts without inventing replies; unfinished items remain visibly labelled draft.
16. Run the applicable Clean generation, QA and Final Gate. Bind each delivered DOCX to an explicit semantic role: Marked roles must retain and validate authorized Track Changes; Clean roles must have none. Never apply a clean-only profile such as `cover-letter` to a Marked file. Routine Plan/Coverage volume or historical style differences alone do not trigger a pause; explicit current author instructions prevail absent a confirmed higher-priority mandatory rule. Report both `verdict` (legacy gate compatibility) and `status` (`PATCH_READY`, `DOCUMENT_READY`, `ROUND_COMPLETE`, `NOT_VERIFIED`, `BLOCKED`); a Patch-scoped gate is never reported as a complete round. Report all files and unresolved exceptions.
16a. After any formal Patch, run `verify-final-round` on the ORIGINAL Plan and its ORIGINAL Verify report, with one `--patch-evidence` per Patch that explicitly lists `supersedes_target_ids`, and bind every final DOCX by `--document PATH=SHA256`. Pass the resulting report to `final-gate` with `--verification-scope round`. Without that report, stop at `PATCH_READY`; never infer `ROUND_COMPLETE` from a `1/1` Patch Verify. Evidence gaps, ambiguous target mapping or hash mismatches are `NOT_VERIFIED`/`BLOCKED`, never a PASS.
17. Support incremental revisions by reusing unchanged inventories and preserving prior apply-report history. Re-inspect only changed source documents or targets whose paragraph structure was affected.
18. Return revised outputs (when applied), response draft, verification evidence, task states and unresolved issues. Never report success without actual output/test evidence.

Formula rule: models may propose LaTeX/UnicodeMath, never hand-authored OMML XML. The deterministic `preview-omml-docx` command may be used to create a separate synthetic Word preview. Do not modify an existing OMML formula in a Manuscript/SI or claim equation Track Changes support; the production equation revision adapter remains blocked until the user accepts the preview in Word after save/close/reopen and the whole-formula revision wrapper has independent validation.

Native Word comment rule: selected text comes only from matching comment range markers. A reference-only comment or containing paragraph is not a substitute for selected text. Exact unique matching is a narrow anchor signal, not the only basis for a global task. Page/line numbers must come from rendered Word layout, never XML paragraph indices.

Delegation and token rule: deterministic parsing, inventory, schema checks and mechanical revision are handled by CLI scripts. Keep the Supervisor context to bounded summaries and cited excerpts. Use cached hashes and avoid repeat parsing. A Worker is optional, not automatic; obey explicit model inspection and user authorization before every worker start.
## Mandatory production editing path and formatting safeguards

- All Manuscript/SI Marked edits MUST use the repository's approved revision-plan/Patch lifecycle and the official CLI Apply/Verify path. Do not create or invoke task-local apply_adapter.py, robust_replace, direct OOXML mutation, format_pass.py, verify_normalized.py, or any other substitute writer/verifier for a production deliverable.
- A failed official preflight, authorization, Apply, Verify, or Final Gate is a hard stop. Preserve the failed plan and evidence, report the exact blocker, and request an engineering change to the repository implementation. Never bypass a fail-closed gate to finish a task.
- A mixed-format replacement may use the official `replacement_format_map` only when every replacement character is explicitly mapped to a source character offset. Each segment has exactly `replacement_start`, `replacement_end`, and `source_offset`; segments must be ordered, contiguous, non-overlapping, and cover the complete replacement. `source_offset` is an offset into the exact `find` text and selects the source Run whose direct formatting will be inherited by that replacement segment. If an author cannot justify the map character-by-character, the operation must fail closed rather than copy the first Run's formatting.
- A `FormatChange` is a separate pure PatchOperation: `find` and `replace` must be identical, `format_authorization.intent` must be explicit, and each `format_operations` entry must identify exact text, scope and typed properties. A format target that modifies inserted text must declare `applies_to_target_index` binding it to that exact preceding replacement target; never inherit sibling format operations by paragraph coincidence. The engine stores the old effective property snapshot in native `w:rPrChange` and verifies only the bound target.
- The verifier compares the complete target paragraph in accepted-text order and checks direct Run formatting per character: unchanged source characters retain their original formatting, mapped insertions inherit their declared source Run, and approved target-bound FormatChange spans are validated against their historical snapshots. Character-level mapping must distinguish individual characters inside a source Run; an explicit scoped script token overrides broader source-derived script expectations within its word. One target's result must never be polluted by another target's formatting failure. A passing substring-presence check is not sufficient.

### One-round QA remediation (Phase 7)

- Remediation is allowed only for a hash-bound `word-final-clean` QA failure on the current Working Clean DOCX recorded in RevisionLedger, and only when every failing check is the local `placeholders` check. Structural/package/XML failures, tracked revisions, comments, formatting/semantic defects, and every other QA failure remain hard stops. The single operation must anchor every exact placeholder token reported by QA and remove all of them in its replacement. Prepare one new single-operation Patch in an immutable batch based on the exact current Marked path and SHA-256; use instruction-based authorization only if the original author instruction explicitly covers the exact correction, otherwise obtain an author decision. The Patch output must be the batch-assigned new Marked path.
- Start the bounded cycle with:

```powershell
python scripts/co_reviewer_cli.py begin-qa-remediation --qa-report "runs/qa-before.quality.json" --revision-ledger revision_ledger.json --batch-dir "runs/batch-<id>" --patch-id "<patch-id>" --reason "Describe the specific local mechanical correction supported by the failed QA evidence." --out "runs/qa-remediation-started.json"
```

- The command proves that the failed QA report is the `word-final-clean` profile and that all failed findings are exact, reported placeholders covered by the Patch find/replace. It binds the failed QA report, source Clean, current Marked hash, approved Patch, batch intent/scope and approval event into RevisionLedger. It refuses a second start for the same RevisionLedger. Then use only the normal `apply`, `verify`, `confirm-verified`, `sync-workflow-ledger`, and `publish-batch` lifecycle. Do not directly modify Clean.
- After the batch is published, compile and QA the new Clean from Marked with:

```powershell
python scripts/co_reviewer_cli.py complete-qa-remediation --state "runs/qa-remediation-started.json" --workflow-ledger workflow_ledger.json --revision-ledger revision_ledger.json --batch-dir "runs/batch-<id>" --clean-out "runs/remediation-final.clean.docx" --qa-report-out "runs/remediation-final.quality.json" --profile word-final-clean --out "runs/qa-remediation-completed.json"
```

- This command regenerates the accepted-changes projection from the exact published Marked bytes, verifies it against the deterministic compiler, updates the RevisionLedger Clean pointer/hash/fingerprint, and performs the second QA pass. A PASS or PASS_WITH_WARNINGS completes remediation. A second QA FAIL records `BLOCKED`; there is no third attempt. The final Release Gate rejects missing, duplicate, incomplete, failed, or hash-mismatched remediation history.
- Classify every repair by its actual cause and context, not by a convenient label. `author_change` is a new author requirement; `engine_defect` is an Apply/format-mapping/engine fix and must never be described as an author request; `qa_remediation` is a document-content fix after a QA failure and must declare `supersedes_target_ids` and consume the single Phase 7 round. Renaming an instruction-based Patch does not consume the QA round, but an authentic QA fix may not use the instruction-based label to evade `remediation_round=1`. Direct Clean edits, Marked overwrites, QA skips, new Rounds and patched task names are forbidden as bypasses.

- At task start, distinguish the Co_Reviewer source worktree, deployed Skill/workflow copy and user's project directory. Run Git root/HEAD/status/version checks only in the identified source worktree. Compare deployed Skill/workflow files with the authorized source snapshot; if provenance/equivalence cannot be confirmed, request confirmation before production execution. A normal-folder project is valid without `.git`; protect its inputs by resolved paths, file existence and SHA-256-bound Round copies. Never conflate source/deployment provenance with project validity.
