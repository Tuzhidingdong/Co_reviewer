# Co_Reviewer V2.3.2 — Frozen Engineering Contract

Status: architecture baseline frozen; implementation is being completed incrementally on the isolated feature branch. This document is normative for implementation. It does not claim that unimplemented or unverified capabilities are complete.

Implementation note (2026-11-18): target-scoped historical Accept/Reject is implemented for native text wrappers, paired move wrappers, and supported property snapshots. Comment/table-topology/numbering cases remain fail-closed. A limited deterministic LaTeX-subset-to-OMML preview DOCX is also available, but it is not a revision writer; existing OMML editing remains disabled pending whole-formula revision-wrapper and Word-version validation.

## Non-negotiable invariants

1. The original source DOCX is immutable. Every candidate is written to a new path.
2. Marked is the sole revision-bearing source of truth. Publication Clean is deterministically compiled from the exact Marked bytes and an explicit revision policy. Clean is never independently repaired.
3. Historical revisions/comments are inventoried before model-intensive discovery. Only historical revision structures intersecting a proposed edit target require a resolution decision; unrelated history is preserved.
4. Every edit is a typed, evidence-linked operation with an explicit Authorized Change intent and Protected Content spans. Deterministic numeric/scientific/reference anchors cannot be reclassified as harmless language drift by the proposing model.
5. WordprocessingML is changed only through structure-specific adapters. Unsupported structures fail closed; no regex/XML string surgery is permitted.
6. All managed DOCX files are members of one package transaction. A release is visible only when its immutable package manifest and final commit marker validate.
7. Cross-file reference relationships are a directed graph of definitions and mentions. Graph discovery does not grant numbering-mutation authority.
8. Phase 7 remediation is allowed at most once. A remediation patch is a formal revision to Marked, followed by mandatory Clean recompilation and a second QA pass. A second failure blocks release.
9. Programmatic checks, GitHub CI, and Windows local tests do not substitute for real Microsoft Word GUI/save-round-trip acceptance.

## State machine

Pre-Flight Inventory (zero model calls) -> Revision Plan / Authorized Change -> Targeted Revision Gate -> Discovery -> Effective Style + conflict arbitration -> Marked package staging -> Clean compilation -> QA/render.

The targeted revision gate runs after targets are mapped but before expensive discovery and before any write. It checks only target overlap. Policies are explicit: ACCEPT_EXISTING, REJECT_EXISTING, or SELECTIVE_ACCEPT_CONFLICTS. No implicit global accept/reject is allowed.

If QA fails on a proven local mechanical issue, remediation_round=0 may create one formal patch targeting Marked. Commit that patch through the normal transaction path, recompile Clean, and re-enter QA with remediation_round=1. A second failure transitions to BLOCKED. Never edit Clean directly.

## Authorization and minimal diff

- Proposed edits must state the reviewer instruction / Authorized Change intent.
- Protected spans are source-coordinate spans and remain immutable unless explicitly authorized.
- The deterministic token lock extracts numeric values and precision, quantities/units, statistical values, chemical formula candidates, citation numbers, and figure/table/equation/section identifiers.
- A token change is blocked unless the exact old token (or typed token) appears in explicitly_authorized_tokens.
- Myers shortest-edit-script narrowing is applied over whitespace-preserving word tokens. Diff output narrows XML mutations; it does not decide whether a change is semantically authorized.
- Unauthorized drift is blocked, not automatically deleted from the proposed text.

## OOXML adapter contracts

### Ordinary text
Only contiguous ordinary Run sequences are editable. A replacement cannot cross fields, OMML, hyperlinks, content controls, bookmark/comment boundaries, drawings, revision wrappers, or unsupported extension structures.

### Formatting
Effective run properties resolve docDefaults, paragraph style inheritance, character style, then direct Run properties. FormatChange snapshots must store the effective prior values for modified dimensions, including explicit false values for inherited boolean properties. A newly inserted w:ins Run stores its target formatting directly in w:rPr and MUST NOT contain w:rPrChange. Existing ordinary Runs may carry w:rPrChange only when the snapshot is valid and non-empty.

### OMML
Models emit LaTeX/UnicodeMath, never hand-written OMML XML. A deterministic converter must create OMML and a schema/Word round-trip adapter must validate it. Formula replacement remains blocked until the converter and revision wrapper have passed supported Word-version acceptance. Whole-formula atomic replacement is the only default mutation mode.

### Structural topology
Splits/merges must preserve field, bookmark, comment-range, list numbering, paragraph properties, and section semantics. If a safe mapping is not proven, block rather than rebalance range markers by copying them. List paragraphs are not merged with non-list paragraphs. PPr/numPr inheritance is explicit.

### Micro-typography
Only explicit typed decisions anchored to the changed text are applied. Minus sign, hyphen, en dash, NBSP, and unit spacing are semantic decisions; no blind global normalization.

## Package transaction and reference graph

All candidate DOCX files are built under a unique staging directory and validated before publication. Multi-file filesystem rename is not assumed to be a true distributed atomic transaction. The immutable version directory is not considered committed until its package manifest hash is referenced by a final commit marker. Readers ignore unmarked candidates. Failure leaves the previous committed package untouched.

Every managed manuscript, SI, and Response Letter DOCX is a graph node. Caption/definition anchors and reference mentions are separately registered. Mentions link only when the target is uniquely resolved; ambiguous or unresolved edges remain explicit. Cross-file numbering changes require explicit package-wide authorization and update only resolved mentions. Static text references are not misrepresented as Word REF fields.

## Verification levels

- Unit tests prove deterministic code behavior only.
- GitHub Actions prove the configured CI matrix only.
- Local Windows tests prove the tested Windows/Python environment only.
- Word GUI open, accept/reject Track Changes, save/reopen, layout/render and PDF correspondence are a separate acceptance tier. No code/CI report may claim that tier without recorded execution evidence.

## Deterministic OMML conversion increment — preview only

A limited LaTeX-subset converter and `preview-omml-docx` CLI command now create a synthetic Word document for formula-rendering inspection. The supported subset includes simple symbols/Greek letters, fractions, square roots, scripts, selected accents and basic text styles. Unsupported commands fail closed. This is not a formula editing adapter: existing OMML remains read-only, and the converter does not create Track Changes. The deterministic converter, whole-formula revision wrapper, and Word save/reopen acceptance are separate requirements; formula editing must remain blocked until all are validated.
## Formatting integrity and production-path enforcement (2026-11-18)

The following controls are normative for the production editing path:

1. Task-local document writers or verifiers are not an alternative to the approved revision-plan/Patch lifecycle. A blocked official gate is a hard stop; it must be resolved in repository code with regression tests, not bypassed by an untracked adapter.
2. Replacements spanning Runs with different direct formatting must fail closed until an explicit formatting map can preserve source formatting. The writer must never silently copy the first Run's bold/italic/font/size/vertical-alignment settings across the entire replacement.
3. Exact Apply verification includes the accepted text sequence for the complete target paragraph, reconstructed from the source DOCX and the ordered operations in the Apply report. Correct revision text in the wrong location is a failure.
4. Benign proofing metadata in word/settings.xml must not block every body edit. Target-local proofing/protected-range markers remain guarded.
5. Protected-token insertions and deletions require individual exact entries in explicitly_authorized_insertions / explicitly_authorized_deletions. A human approval intent alone does not authorize an arbitrary bundle of numbers, units, formulae, or citations.
6. The internal run-property setter retains its explicit removal semantics for None; callers must not overload None to mean True. Bold/italic format operations require a typed, explicit value.

These controls do not replace Microsoft Word save/reopen acceptance or the author's visual and scientific review.
